01 — System Overview & Component Architecture

Infrastructure

System Architecture

  • Frontend: React 18 + TypeScript SPA with Vite, lazy-loaded routes, context-based state
  • Security: Stateless JWT in HttpOnly cookies, CSRF via XSRF-TOKEN, 5-layer filter chain
  • API: 30+ REST controllers under /api/**, DTO validation with Jakarta
  • Business: 35+ services handling auth, feed, projects, billing, GitHub, messaging
  • Persistence: Spring Data JPA repositories, MySQL 8 (prod) / H2 (dev/test), Flyway migrations
  • Real-time: STOMP over WebSocket at /ws with JWT auth, rate limiting, typing/presence
  • External: Razorpay + Stripe payments, GitHub OAuth + API, SMTP email, Sentry
  • Infrastructure: Docker multi-stage builds, Vercel/Railway deployment, @Scheduled jobs

Key Design Decisions

  • Stateless sessions (no server-side HTTP session)
  • Access token in HttpOnly cookie, never in JS
  • Refresh token rotation with reuse detection
  • Pessimistic locks on payment updates (race prevention)
  • OAuth2 login is optional (conditional bean registration)
  • Admin routes require hasRole("ADMIN")
  • Webhook endpoints exempt from CSRF (verified by provider signature)

Source Files & Responsibilities

config/SecurityConfig.java — Defines the entire HTTP security filter chain, CSRF rules, CORS, session policy, header hardening (HSTS, frame-options, referrer), and route-level authorization (permitAll vs authenticated vs ADMIN).
config/WebSocketConfig.java — Configures STOMP message broker (/topic, /queue), application destination prefix (/app), user prefix (/user), SockJS fallback endpoint (/ws), and registers JwtStompChannelInterceptor for WebSocket-level auth.
config/JwtStompChannelInterceptor.java — Intercepts STOMP CONNECT/SUBSCRIBE frames, validates JWT from Authorization header, sets SecurityContext, enforces per-user subscription quotas.
config/CsrfConfig.java — CookieCsrfTokenRepository, CSRF cookie filter, and the set of paths exempt from CSRF (webhooks, public API, auth/refresh).
config/JwtTokenProvider.java — Generates and validates JWT access/refresh tokens, extracts user claims.
DevSyncApplication.java — Spring Boot entry point with @EnableScheduling for @Scheduled jobs (subscription sync, pending registration cleanup).
frontend/src/main.tsx — React Router setup with lazy-loaded routes, AuthProvider, SubscriptionProvider, ProtectedRoute/AdminRoute guards, ThemeProvider, ScrollToTop.
frontend/src/api.ts — Axios instance with base URL, CSRF header injection, 401 interceptor for automatic token refresh.
application.yml — All Spring Boot configuration: datasource, JWT secrets, mail, billing providers, GitHub OAuth, rate limits, upload limits, management endpoints.

02 — Security Filter Chain

What Starts the Flow

Every HTTP request to the Spring Boot backend passes through the security filter chain defined in SecurityConfig.

Step-by-Step

  • 1. CsrfCookieFilter — Always sets XSRF-TOKEN cookie; CsrfFilter validates X-XSRF-TOKEN header on POST/PUT/DELETE
  • 2. RateLimitingFilter — General configurable rate limiting
  • 3. JwtAuthenticationFilter — Reads access_token from HttpOnly cookie, validates JWT, loads UserDetails, sets SecurityContext
  • 4. SpamProtectionFilter — Per-user rate limit for abuse-prone endpoints (invitations, follows, reports)

Important Decisions

  • CSRF exempt: /api/billing/webhook/**, /ws/**, /api/public/**, /api/auth/refresh
  • Auth exempt: /api/auth/**, /api/github/callback, /api/webhooks/github
  • Admin-gated: /api/admin/** requires hasRole("ADMIN")
  • Session: STATELESS (no server-side HTTP session)

Source Files & Responsibilities

config/SecurityConfig.java — Master security configuration. Registers all filters in order, defines route authorization rules, configures CORS, sets session policy to STATELESS, adds response headers (frame-deny, referrer-policy, HSTS in prod). Controls whether CSRF/OAuth are enabled via app properties.
config/CsrfConfig.java — CookieCsrfTokenRepository backed by HTTP session, CsrfTokenRequestHandler for double-submit cookie pattern, and the CsrfCookieFilter that always sets XSRF-TOKEN cookie on responses. Maintains the list of CSRF-exempt paths.
auth/JwtAuthenticationFilter.java — OncePerRequestFilter that reads access_token from HttpOnly cookie, validates JWT signature and expiry via JwtTokenProvider, loads UserDetails from DB, and sets UsernamePasswordAuthenticationToken in SecurityContext. Returns 401 JSON if token is invalid.
auth/JwtTokenProvider.java — Generates JWT access tokens (15min) and refresh tokens (30d) with HS256 signing. Extracts userId/email claims. Validates token integrity, checks expiry, and handles malformed tokens.
auth/RateLimitingFilter.java — General-purpose rate limiter filter placed before authentication. Uses configurable per-endpoint limits. Returns 429 with Retry-After header when exceeded.
ratelimit/SpamProtectionFilter.java — Per-user rate limiter for abuse-prone POST endpoints: invitations (10/min), follows (30/min), reports (5/min). Runs AFTER authentication so it can key on userId. Uses in-memory buckets (single-instance only).
ratelimit/RateLimiter.java — Core rate-limiting engine using sliding window counters. Supports per-user and per-IP limiting. Configurable window size and max requests.
config/JwtStompChannelInterceptor.java — WebSocket equivalent of JwtAuthenticationFilter. Intercepts STOMP CONNECT frames, validates JWT from Authorization header, and enforces per-user subscription/message quotas for WebSocket traffic.

03 — Authentication — Email Registration (OTP Verification)

What Starts the Flow

User clicks "Create account" on the Auth.tsx signup form after entering name, username, email, and password.

Step-by-Step

  • 1. Frontend POSTs to /api/auth/register/initiate
  • 2. PendingRegistrationService checks: email exists? username taken?
  • 3. Generates 6-digit OTP, stores SHA-256 hash in PendingRegistration table
  • 4. Sends OTP via SMTP (EmailService)
  • 5. Frontend shows VerifyEmail.tsx with 6-digit OTP input
  • 6. User enters OTP, frontend POSTs to /api/auth/register/verify
  • 7. Backend verifies OTP using constant-time comparison (timing-safe)
  • 8. On success: creates User, generates JWT access + refresh tokens, records audit log
  • 9. Sets HttpOnly cookies for access + refresh tokens

Important Decisions

  • Email exists: Rejected immediately (before sending OTP)
  • OTP expired: PendingRegistration deleted, user must re-register
  • Too many attempts: After 5 failures, PendingRegistration deleted
  • Resend: 60-second cooldown, invalidates previous OTP

Security

  • Only SHA-256 hash of OTP is stored (not plaintext)
  • Constant-time comparison prevents timing attacks
  • @Scheduled hourly cleanup of expired PendingRegistrations
  • No account exists until OTP verification succeeds

Source Files & Responsibilities

frontend/pages/Auth.tsx — Login/SignUp form with email, password, username fields. Handles form validation, calls register/initiate API, shows password visibility toggle, switches between Sign In and Sign Up modes.
frontend/pages/VerifyEmail.tsx — 6-digit OTP input screen shown after registration initiation. Auto-advances between digit fields, supports paste, shows countdown timer, resend button with cooldown, and loading state during verification.
backend/auth/AuthController.java — REST endpoints: POST /register/initiate (creates pending + sends OTP), POST /register/verify (verifies OTP + creates account), POST /register/resend (new OTP with cooldown). Returns JWT cookies on successful verification.
backend/auth/PendingRegistrationService.java — Core OTP logic: generates 6-digit OTP, hashes with SHA-256, stores hash only in DB, enforces 5-attempt limit, 60-second resend cooldown, 10-minute expiry. @Scheduled hourly cleanup of expired registrations.
backend/auth/entity/PendingRegistration.java — JPA entity storing: email, passwordHash, fullName, username, otpHash, expiresAt, failedAttempts. hasExpired() checks LocalDateTime.now() against expiresAt.
backend/auth/repository/PendingRegistrationRepository.java — Spring Data JPA repository with findByEmail() for looking up pending registrations by email address.
backend/auth/EmailService.java — SMTP email sender using Spring Mail. sendOtpEmail() formats and sends the 6-digit verification code. Throws if SMTP is not configured (MAIL_USERNAME/MAIL_PASSWORD missing), so frontend gets a meaningful error.
backend/auth/AccountToken.java — Entity for password-reset and email-verification tokens (separate from OTP flow). Used by AccountRecoveryService for forgot-password links.

04 — Authentication — Login & JWT Token Lifecycle

What Starts the Flow

User enters email/username + password on Auth.tsx login form.

Step-by-Step

  • 1. Frontend POSTs to /api/auth/login
  • 2. AuthService.findUserByIdentifier() — detects email vs username by "@"
  • 3. passwordEncoder.matches() — BCrypt comparison
  • 4. ensureAccountActive() — blocks deleted/blocked accounts
  • 5. Generates JWT access token (15min) + refresh token (30 days)
  • 6. Sets HttpOnly cookies — tokens never reach JavaScript
  • 7. Redirects to /dashboard

Token Refresh

  • Axios interceptor catches 401 → calls /api/auth/refresh
  • RefreshTokenService.rotate() validates, detects reuse, issues new pair
  • New cookies set, original request retried transparently

WebSocket Auth

  • GET /api/auth/ws-token provides short-lived token for STOMP CONNECT
  • Browser can't attach HttpOnly cookies to WebSocket frames

Source Files & Responsibilities

frontend/pages/Auth.tsx — Login form UI with email/username + password. Handles form submission, error display, toggle password visibility, switches to SignUp mode.
frontend/services/authService.ts — API client for auth endpoints: login(), refreshToken(), logout(), register(), getCurrentUser(). Wraps axios calls with error handling.
frontend/api.ts — Axios instance with request/response interceptors: injects X-XSRF-TOKEN header from cookie, catches 401 responses and triggers automatic token refresh via /api/auth/refresh, retries original request with new token.
backend/auth/AuthController.java — REST endpoints: POST /login (authenticates + sets cookies), POST /refresh (rotates refresh token), POST /logout (revokes + clears cookies), GET /me (returns current user), GET /ws-token (short-lived token for WebSocket).
backend/auth/AuthService.java — Core auth logic: login() validates credentials via BCrypt, checks account active status, generates JWT pair, records audit log. refreshToken() delegates to RefreshTokenService.rotate(). findUserByIdentifier() detects email vs username by presence of @.
backend/auth/JwtTokenProvider.java — JWT token creation and validation. generateAccessToken() creates HS256-signed token with userId/email claims, 15-minute expiry. getUserIdFromToken() extracts claims. validateToken() checks signature and expiry.
backend/auth/RefreshTokenService.java — Refresh token lifecycle: issue() creates token + stores hash in DB with IP/UA. rotate() validates presented token (type, signature, expiry, registry lookup), detects reuse (revokes entire family if stolen token replayed), issues new pair. revoke() marks token as revoked.
backend/auth/RefreshTokenCookie.java — Creates/clears the refresh_token HttpOnly cookie (30-day expiry, Secure flag in prod, SameSite=Lax). Never exposed to JavaScript.
backend/auth/AccessTokenCookie.java — Creates/clears the access_token HttpOnly cookie (15-minute expiry). Short-lived to limit exposure if stolen.

12 — Real-time Messaging (WebSocket / STOMP)

What Starts the Flow

Messages.tsx page opens → WebSocketService establishes STOMP connection.

Step-by-Step

  • 1. Frontend fetches short-lived access token from /api/auth/ws-token
  • 2. SockJS connects to /ws with token in STOMP CONNECT Authorization header
  • 3. JwtStompChannelInterceptor validates token, sets SecurityContext
  • 4. Frontend subscribes to user-specific topics
  • 5. Messages sent via /app/message.send → WebSocketController → MessageService → DB
  • 6. SimpMessagingTemplate pushes to /topic/chat/{roomId} for all subscribers

Key Topics

  • /topic/chat/{roomId} — message delivery
  • /topic/typing/{roomId} — typing indicators
  • /topic/presence — online/offline status
  • /user/topic/notifications/{userId} — push notifications
  • /topic/subscription/{userId} — subscription changes

Source Files & Responsibilities

frontend/services/websocketService.ts — WebSocket/STOMP client singleton. connect(token) establishes SockJS connection to /ws, subscribes to user topics, handles reconnection with exponential backoff. Exposes sendMessage(), startTyping(), stopTyping() methods. Manages connection status (Connected/Reconnecting/Disconnected).
frontend/pages/Messages.tsx — Main messaging page. Shows ConversationList sidebar + MessageList main area. Handles search users for new DM, creates conversations, loads message history.
frontend/components/messages/ConversationList.tsx — Sidebar showing all conversations (DMs + team rooms). Sorted by last message time, shows unread badge, partner avatar/name, last message preview. Click loads conversation.
frontend/components/messages/MessageList.tsx — Message display area. Renders messages chronologically, shows sender avatar, timestamp, read receipts, reactions. Auto-scrolls to bottom on new message. Context menu for edit/delete.
frontend/hooks/useTyping.ts — React hook that manages typing indicator state. Sends typing.start/stop via WebSocket, receives typing events from other users, auto-timeout after 3 seconds of inactivity.
backend/message/WebSocketController.java — STOMP message handler. @MessageMapping("/app/message.send") receives SendMessageRequest, delegates to MessageService.sendMessage(), returns MessageResponse. Handles typing indicators via /app/typing.start and /app/typing.stop.
backend/message/MessageController.java — REST endpoints: GET /api/messages/conversations (list), GET /api/messages/dm/{userId} (DM history), GET /api/messages/room/{roomId} (room history), POST /api/messages (send via REST fallback), PUT /api/messages/{id} (edit), DELETE /api/messages/{id} (soft delete).
backend/message/MessageService.java — Core messaging logic: sendMessage() validates participants, persists to DB, broadcasts via SimpMessagingTemplate to /topic/chat/{roomId}, creates notification for offline users. getConversations() batch-loads partner users. markDirectRead() marks messages as read.
backend/config/WebSocketConfig.java — Configures STOMP broker (/topic, /queue), application prefix (/app), user prefix (/user), registers /ws endpoint with SockJS fallback, sets allowed origins.
backend/config/JwtStompChannelInterceptor.java — Intercepts STOMP CONNECT/SUBSCRIBE frames, validates JWT from Authorization header, sets SecurityContext for message handlers, enforces subscription quotas.
backend/presence/PresenceController.java — Handles presence heartbeats. User periodically calls update() to report online/away/offline status. Broadcasts to /topic/presence for all connected users.

14 — Billing — Subscription & Checkout Flow

What Starts the Flow

User clicks "Upgrade" on Billing.tsx after selecting a plan and payment provider.

Step-by-Step

  • 1. Frontend POSTs to /api/billing/checkout with planCode + provider
  • 2. PlanBillingValidator checks plan validity and current subscription
  • 3. Routes to RazorpayClient or StripeClient based on provider
  • 4. Provider returns orderId/session.url → frontend redirects to provider
  • 5. User completes payment on provider page
  • 6. Provider sends webhook to /api/billing/webhook/{razorpay|stripe}
  • 7. Webhook verified (signature check), idempotent (WebhookEvent dedup)
  • 8. handlePaymentCaptured() with pessimistic lock → Payment = SUCCESS
  • 9. Subscription created/upgraded, WebSocket broadcast, audit log

Security

  • Webhook endpoints exempt from CSRF (provider signature verification)
  • Pessimistic lock on Payment prevents concurrent activation
  • WebhookEvent insertIfAbsent prevents duplicate processing

Source Files & Responsibilities

frontend/pages/Billing.tsx — Billing settings page. Shows current plan, upgrade options (Razorpay/Stripe), payment history, refund request form. Displays plan features, usage limits, subscription status.
frontend/services/billingService.ts — API client for billing: checkout(), getSubscription(), getPayments(), getUsage(), cancelSubscription(), submitRefundRequest(). Wraps axios calls.
backend/billing/BillingController.java — User-facing REST endpoints: POST /api/billing/checkout (create payment), GET /api/billing/subscription (current plan), GET /api/billing/payments (history), POST /api/billing/cancel (cancel subscription), POST /api/billing/refund-requests (request refund).
backend/billing/BillingService.java — Core billing orchestrator: createCheckout() validates plan via PlanBillingValidator, routes to RazorpayClient or StripeClient, saves Payment(PENDING). handlePaymentCaptured() with pessimistic lock transitions Payment→SUCCESS, creates/upgrades Subscription, broadcasts via WebSocket. handlePaymentRefunded() transitions Payment→REFUNDED, completes RefundRequest if APPROVED, revokes subscription.
backend/billing/BillingWebhookController.java — Razorpay webhook endpoint: POST /api/billing/webhook/razorpay. Receives raw payload + X-Razorpay-Signature, delegates to BillingService.handleRazorpayWebhook(). Exempt from CSRF.
backend/billing/StripeWebhookController.java — Stripe webhook endpoint: POST /api/billing/webhook/stripe. Receives raw payload + Stripe-Signature, delegates to BillingService.handleStripeWebhook(). Exempt from CSRF.
backend/billing/RazorpayClient.java — Razorpay API wrapper: createOrder() creates payment order, refundPayment() initiates refund. Handles API errors, timeout (10s), retries.
backend/billing/StripeClient.java — Stripe API wrapper: createCheckoutSession() creates hosted checkout page, refundPayment() creates refund. Handles API errors, idempotency keys.
backend/billing/PlanBillingValidator.java — Validates checkout requests: plan exists, user not already on same plan, upgrade path valid (FREE→STARTER→PRO→ENTERPRISE), downgrade allowed.
backend/billing/EntitlementService.java — Plan limit enforcement: checks user's subscription against limits (max projects, max members, max tasks). Throws FeatureLimitException if exceeded. Used across project, task, and member operations.
backend/billing/entity/Payment.java — JPA entity: id, userId, planCode, amount, currency, status (PENDING/SUCCESS/FAILED/REFUNDED), provider (RAZORPAY/STRIPE), providerOrderId, providerPaymentId. Indexed on userId + status.
backend/billing/entity/Subscription.java — JPA entity: id, userId, planCode, status (ACTIVE/CANCELLED/PAST_DUE/TRIALING), provider, providerSubscriptionId, currentPeriodEnd. One active subscription per user.

15 — Billing — Refund Lifecycle

What Starts the Flow

User requests a refund from Billing.tsx → Admin approves in AdminBilling → Provider processes → Webhook confirms.

State Machine

  • PENDING → APPROVED → COMPLETED (happy path)
  • PENDING → REJECTED (admin rejects)
  • COMPLETED only set by webhook — admin approval stays at APPROVED

Key Design Decision

  • Webhook is the source of truth for refund completion
  • Admin approval only sets APPROVED, not COMPLETED
  • completeRefundRequestIfApproved() transitions APPROVED → COMPLETED only
  • Idempotent: duplicate webhooks are no-ops

Subscription Revocation

  • Only revokes if plan matches and subscription is ACTIVE/PAST_DUE/TRIALING
  • Newer payment protection: won't revoke if a newer SUCCESS payment exists
  • Stripe subscription cancellation (best-effort) preserved

Source Files

backend/billing/BillingService.java — submitRefundRequest() creates PENDING RefundRequest. approveRefundRequest() transitions PENDING→APPROVED (admin only). completeRefundRequestIfApproved() transitions APPROVED→COMPLETED (called from webhook handlers). Subscription revocation happens on COMPLETED.
backend/billing/BillingController.java — POST /api/billing/refund-requests (user submits), GET /api/billing/refund-requests (user's own requests).
backend/billing/AdminBillingController.java — Admin endpoints for reviewing refund requests: approve, reject. Queries all pending requests.
backend/billing/entity/RefundRequest.java — JPA entity: id, userId, paymentId, reason, status (PENDING/APPROVED/REJECTED/COMPLETED), reviewedBy, reviewedAt. Indexed on userId + status.
backend/billing/entity/RefundRequestStatus.java — Enum: PENDING, APPROVED, REJECTED, COMPLETED. State machine: PENDING→APPROVED→COMPLETED or PENDING→REJECTED.
backend/billing/repository/RefundRequestRepository.java — JPA repository: findByPaymentId() for webhook lookup, findByPaymentIdAndStatus() for idempotent completion, findByUserId() for user's requests.
frontend/pages/Billing.tsx — User-facing refund request form: select payment, enter reason, submit. Shows status of existing requests.
frontend/pages/AdminBilling.tsx — Admin refund management: lists all pending/approved/rejected/completed requests, approve/reject buttons, filter by status.

17 — GitHub Integration — OAuth & Repository Linking

What Starts the Flow

User clicks "Connect GitHub" in Settings → GitHubSection.tsx.

Step-by-Step

  • 1. Frontend redirects to GitHub OAuth authorize URL
  • 2. User authorizes on github.com
  • 3. GitHub redirects to /api/github/callback with code
  • 4. GitHubOAuthClient exchanges code for access_token
  • 5. GitHubTokenCrypto.encrypt(token) with AES
  • 6. Encrypted token saved in GitHubLink table
  • 7. User can then link repos to projects

API Calls Through GitHubClient

  • All GitHub API calls go through GitHubClient
  • Token is decrypted before each call
  • Rate limit headers tracked
  • 10s timeout per request

Source Files & Responsibilities

frontend/components/GitHubSection.tsx — GitHub integration UI in Settings. Shows connect/disconnect button, linked repos list, repo selection for linking to projects. Handles OAuth redirect flow.
backend/github/GitHubController.java — GET /api/github/callback (OAuth callback, exchanges code for token), GET /api/github/status (check connection), POST /api/github/link (link repo to project), DELETE /api/github/unlink.
backend/github/GitHubIntegrationService.java — Manages GitHub OAuth flow: generates authorize URL, exchanges code for access_token, encrypts token via GitHubTokenCrypto, stores in GitHubLink table.
backend/github/GitHubOAuthClient.java — HTTP client for GitHub OAuth token exchange: POST https://github.com/login/oauth/access_token with code + client_id + client_secret. Returns access_token.
backend/github/GitHubClient.java — GitHub API v3 REST client: fetches commits (/repos/{owner}/{repo}/commits), issues (/repos/{owner}/{repo}/issues), PRs (/repos/{owner}/{repo}/pulls), branches (/repos/{owner}/{repo}/branches). Handles rate limits, 10s timeout, decrypts token before each call.
backend/github/GitHubProjectService.java — Links GitHub repos to DevSync projects: validates repo access, stores owner/repo/defaultBranch in GitHubProjectLink, fetches initial repo details.
backend/github/GitHubTokenCrypto.java — AES encryption/decryption for GitHub access tokens. encrypt() before storage, decrypt() before API calls. Uses GITHUB_TOKEN_ENCRYPTION_KEY env var.
backend/github/GitHubWebhookController.java — POST /api/webhooks/github (public endpoint). Verifies X-Hub-Signature-256, routes push/PR events to GitHubWebhookService.
backend/github/GitHubWebhookService.java — Processes webhook events: updates task PR status, syncs commit data, triggers notifications. Idempotent via event deduplication.

31 — Deployment & Infrastructure

Development

  • Backend: mvn spring-boot:run (dev profile, H2, DataSeeder)
  • Frontend: bun run dev (Vite on :5173, proxy to :8080)
  • Zero configuration needed for local dev

Production

  • Backend: Railway — Docker multi-stage build, prod profile
  • Frontend: Vercel — npm run build, SPA rewrites
  • MySQL: external (Railway add-on or external host)
  • Fail-fast: application won't start without JWT_SECRET, DB credentials

Docker

  • docker-compose.yml with backend, frontend, mysql services
  • Multi-stage build: maven build → JRE runtime (alpine)

Key Security

  • prod profile has NO defaults for secrets (fail-fast)
  • ProductionConfigValidator rejects dev fallback values
  • HSTS enabled in prod, CSRF cookie-based
  • Rate limiting, spam protection, WS rate limiting
